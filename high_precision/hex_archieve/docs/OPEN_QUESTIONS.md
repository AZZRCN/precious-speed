# 待请教问题清单 — HEX 大整数乘法优化

> 版本：2026-08-11
> 提问方：本项目开发（AI 协作）
> 全部数据均在 VM（Intel Tiger Lake）实测，`perf stat`，`taskset -c 5` 绑核，重复 3 次取中位。
> 编译口径统一：`g++ -O2 -march=x86-64-v3 -std=c++23`

---

## 0. 背景（30 秒）

**赛题**：纯 16 进制串大整数 `mul` / `div` / `add`，LC 评测机为 **AMD Zen3**，计分口径为 **CPU 时间（用户态 + 内核态总和）**（`docs/HANDBOOK.MD:23`）。

**现有实现（v13，当前最优候选）**：
- 64-bit limb，基底 `2^k`（**不是** 10^x），`pick_k` 用 `gk[i] = (19-i) << (2i+4)` 分档，保证 `2^(2k)·lm ≡ 2^48` 恒定
- FFT：radix-4 自排序，AVX2 `__m128d` 复数蝶形
- 点乘：实数 FFT 共轭对称打包（`pointwise` / `pointwiseSq`）
- zero-hi 优化：高半区全零时省一半清零 + `difRecZeroHi` 省一半读流量

**本轮尝试（v16）**：从前人的十进制实现 `div_verifield.cpp` 移植 **radix-3 / radix-5 混合基蝶形**，让 FFT 长度档位从纯 `2^k` 细化到 `2^k / 3·2^(k-2) / 5·2^(k-3)`，理论上把平均长度浪费从 ~1.33× 压到 ~1.1×。

## 1. 【核心卡点】IPC 悖论：三项指标全赢，cycles 却输

这是目前最想不通的一件事。

### 1.1 全量数据（22 个测试点，统一负重）

| 指标 | v13w（基线） | v16（混合基） | ratio A/B | 谁更好 |
|---|---|---|---|---|
| instructions:u | 2,187,996,946 | 2,183,755,129 | 1.0019 | **v16 少 0.19%** |
| L1-dcache-load-misses | 50,938,472 | 50,647,238 | 1.0058 | **v16 少 0.58%** |
| cache-misses (LLC) | 13,998,818 | 13,934,802 | 1.0046 | **v16 少 0.46%** |
| **cycles:u** | **826,494,500** | **836,896,232** | **0.9876** | **v16 多 1.24%** ← |
| 正确性 | bad=0/22 | bad=0/22 | — | 均通过 |

> ratio = A/B，**< 1 表示 B（v16）更差**。

### 1.2 归因到混合档用例（IPC 逐点）

| case | 走混合档? | IR ratio | CYC ratio | v13w IPC | v16 IPC | ΔIPC |
|---|---|---|---|---|---|---|
| large_00 | 是（radix-3） | 0.9875 | **0.8752** | 3.106 | 2.753 | **−11.4%** |
| large_01 | 是 | **1.0382**（v16 指令更少 3.8%） | **0.9419** | 3.137 | 2.846 | **−9.3%** |
| large_02 | 是 | 0.9996（持平） | **0.8849** | 3.087 | 2.732 | **−11.5%** |
| max_max_01 | 否（纯 2 幂） | 1.0000（逐指令相同） | 0.9875 | 2.615 | 2.583 | −1.2%（噪声） |
| fft_killer_00 | 否 | 1.0000 | 1.1117 | — | — | 噪声 |

**对照组极干净**：非混合档的 IR ratio 精确等于 `1.0000`（同一份 2 幂代码路径，逐指令一致），说明测量口径没问题。

**问题就在混合档**：`large_01` 指令数比基线**还少 3.8%**，cycles 却多 6.2%。`large_02` 指令数持平，cycles 多 13%。

### 1.3 已排除的解释

| 假说 | 排除依据 |
|---|---|
| 代码膨胀 / I-cache | 非混合档 IR=1.0000 且 cycles 基本持平；BSS 完全相同 |
| L1 miss 变多 | 全量 L1M v16 更少 0.58% |
| LLC miss 变多 | 全量 LLC v16 更少 0.46%（但 `large_00` 单点 v16 多 13.5%，见 Q5） |
| harness 位置偏差 | v13copy vs v13 自比 = 0.9959；反向位置比值互为倒数，自洽 |
| 蝶形未向量化 | **已向量化**（下节），IPC 仍掉 |

### 1.4 已经做过的向量化

初版顶层 radix-3/5 蝶形是标量 `__m128d` 逐点。已改写成 AVX2（一次处理 2 个 complex，与 radix-4 同规格），效果：

- `large_00` IR ratio：0.9583 → **0.9875**（多出的指令从 4.4% 压到 1.3%）
- `large_01` IR ratio：0.9847 → **1.0382**（反超基线）
- 但 **cycles 几乎没动**（TOTAL 0.9853 → 0.9876）

**即：省下来的指令没有兑现成 cycles。**

### ❓ Q1（最想问的）

指令数、L1 miss、LLC miss 三项全部持平或更优，cycles 却系统性多 6~14%，IPC 掉 9~11.5%。
**这种情况下最可能的瓶颈是什么？我应该优先测哪个 PMU 事件来定位？**

我的怀疑方向（未验证）：

1. **stride-m 访存导致 4K aliasing / DTLB 压力**
   顶层 radix-3/5 蝶形同时读写 `b0[c]`、`b0[m+c]`、`b0[2m+c]`（radix-5 是 5 路），`m` 为 2 的幂（64 ~ 32768）。当 `m·16 B` 是 4096 的倍数时，3~5 个流的地址低 12 位完全相同 → store-to-load forwarding 冲突 / L1 bank conflict。
   radix-4 也有 4 路 stride，但它是自排序（自带地址置换），可能天然错开了。
   **想问**：Zen3 上这种同余 stride 多流是不是已知坑？常规规避手法是 padding（每 m 个元素插一个 dummy）还是改数据布局？

2. **依赖链过长（尤其 radix-5）**
   radix-5 蝶形的关键路径：`t1..t4` → `u1/u2, v1/v2`（各 2 次 FMA）→ `A1..A4` → 4 次 `cmul`。目测 ~10 级 FP 依赖，而 radix-4 只有 ~4 级。若每个 lane 的依赖链没被相邻 `c` 的循环展开填满，就会流水线空转 —— **这刚好符合"指令数不变但 IPC 掉"的特征**。
   **想问**：这个方向值不值得投入？如果值得，是手工展开 4 路 `c` 更好，还是把 radix-5 拆成 radix-4 风格的多级小蝶形？

3. **`pointwise_mixed` 的反向遍历**
   混合基频域点乘要做跨块共轭配对：块 `j` 的位置 `p` ↔ 块 `R-j` 的位置 `m-1-p`。后者是**递减**遍历，硬件预取器对下降流的支持通常弱于上升流。
   **想问**：这类"一升一降"配对访问有没有标准优化范式？（比如预先把降序流反转到临时缓冲）

## 2. 运行时 / 启动开销（这块我走过弯路，想请前辈评判）

### 2.1 事实

同一份编译命令，只因源码是否用到 `std::vector` / `new[]`，二进制的 `DT_NEEDED` 会差出 `libstdc++.so.6` + `libgcc_s.so.1`。动态链接器解析这两个库的成本实测：

| 二进制 | DT_NEEDED | example_00 instructions:u |
|---|---|---|
| v13（裸） | libm, libc | **148,530** |
| v13w（注入 vector 负重） | + libstdc++ | 1,776,074 |
| v16 | + libstdc++, libgcc_s | 1,782,629 |
| **wbmul（假想敌，LC 榜首）** | + libstdc++, libgcc_s | **1,832,996** |

即 **~1.63M 条固定启动指令**，且 LC 按 CPU 时间计分，这笔钱**会被计入**。

### 2.2 我最初的错误处理

我一度把这 1.63M 当成"我方缺陷"，开始追查怎么从源码消除 libstdc++ 依赖。
**被叫停了，理由是**：假想敌 `web_best/mul.cpp` 满是 `std::vector` / `new u64[]` / `std::string`，同样背这笔税，**甚至比我们还多 5 万条**。这是全场公共成本，不是竞争劣势。抠它属于"投机取巧"，不是赛题。

**改正后的做法**：建立"统一负重台" —— 给基线 v13 注入等价的 `std::vector` + unwind 引用，使其 `DT_NEEDED` 与候选完全一致（`objdump -p | grep NEEDED` 逐项核对），**之后所有 A/B 都在统一负重下进行**。原稿备份在 `web_best/origin/`。

这一改动直接**推翻了上一轮结论**：v16 原本测出 −6.8%，统一负重后真实差距只有 **−1.24%**。

### ❓ Q2

统一负重这个做法对不对？有没有更规范的公平对照方式？
（我目前的实现是往基线 `main()` 里插一段 `static std::vector<double>` + `asm volatile` 屏障，防止被优化掉。感觉有点土。）

### ❓ Q3

最终提交前把 libstdc++ 依赖真正消掉（改用静态数组 / `mmap`），能白赚 1.63M 指令。
**这算不算正当优化？还是说属于钻空子、应该避免？**
（当前 `submit_ready/mul.cpp` 因为 `new cpx[]` 而背着这笔税。）

## 4. 混合基路线本身的取舍

### 现状

v16 的混合基路径走的是**全复数 FFT**，因此放弃了 v13 的两个优势：
1. 实数 FFT 共轭对称打包（长度减半）
2. zero-hi 优化

前人的十进制实现 `div_verifield.cpp` 里，混合基是**长在实数 FFT 框架内**的（`rdif` / `ridit` / `real_conv` / `real_dot_binrev3` / `real_dot_binrev5`，L2546/2587/2626/2644）。我只搬了蝶形，没搬实数框架。

理论收益：长度从 `2^k` 细化后可降到 0.75× / 0.625×，实测确实兑现（IR 已持平甚至更优），但常数变差把收益吃掉了。

### ❓ Q6

值不值得把整套实数混合基框架（`real_dot_binrev3/5` + zero-hi）也移植过来？
工作量不小，而且我在移植蝶形时已经踩过一次坑：

> 原以为槽位（块 j, 位置 p）承载的频点是 `phi = R·brev_m(p) + j`，实测**错**。
> 用冲激反解出真实排列，最终得到解析式 `phi(j,p) = R·((m − brev_m(p)) mod m) + j`，R=3/R=5 逐项吻合。

实数框架的频点映射只会更绕。**在 IPC 问题没解决之前先做这个，是不是本末倒置？**

### ❓ Q7（小事实核对）

前辈说 `div_verifield.cpp` 里 "radix 3, 5, 7 都有"。
我通读 7069 行全文，**只找到 radix-3 和 radix-5**（`dif3Stage`/`idit3Stage`/`dif5Stage`/`idit5Stage` + `FFTTable3`/`FFTTable5`）。
**radix-7 是不是在 `best` 的另一个文件里？** 如果有，值得一并移植（长度粒度会更细）。

## 6. 附：已确认无误的部分（不用怀疑这些）

- **基底问题**：v16 是纯 `2^k` 位级基底（`split_b2` 用掩码 `(1u<<k)-1` + 位偏移 `j*k`），`grep` 全文无任何十进制常量残留。DEC 参考实现虽然是 `BASE = 10^4`，但我只搬了**变换层**（蝶形 / 旋转因子），那层不吃基底。
- **正确性**：v16 三条路径（radix-3 / radix-5 / 纯 2 幂）全部通过 22 点 `.exp` md5 逐字节比对，bad=0。隔离自测中 FFT 往返误差 3.4e-13，`pointwise_blk` 误差 0.0。
- **测量口径**：harness 自比 0.9959，反向位置互为倒数，无系统偏差。非混合档 IR 精确 1.0000。

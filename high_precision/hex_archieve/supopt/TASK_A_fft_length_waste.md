## 1. 一句话

**当前 FFT 长度只能取 2 的幂，导致最坏情况下 50% 的运算量花在零填充上。
实测在几个常见规模上浪费达到 2.00×。请把它消掉。**

## 2. 硬数据 —— 浪费有多大

现役代码的长度选择逻辑（`work/mul/v10c.cpp`）：

```cpp
// u = na + nb  (结果的 64-bit limb 数)
static inline int pick_k(size_t u) {
    static const size_t gk[11] = {19ull << 4,  18ull << 6,  17ull << 8, 16ull << 10,
                                  15ull << 12, 14ull << 14, 13ull << 16, 12ull << 18,
                                  11ull << 20, 10ull << 22, ~size_t(0)};
    int i = 0;
    while (u > gk[i]) ++i;
    return 19 - i;                       // k = 每个 double 系数装多少 bit
}

const int k = pick_k(u);
const u32 coeffs = (u32)(u * 64 / k) + 1;         // 结果需要的实系数个数
const u32 lm = 2u << (31 - __builtin_clz(coeffs)); // 向上取到 2 的幂
const u32 ts = lm >> 1;                            // 复 FFT 点数（实数打包）
```

`gk` 表的含义是 **"用 k 位一组时，结果 limb 数 u 最多能到多少而精度仍安全"**：

| k | u 上限 |
|---|---|
| 19 | 304 |
| 18 | 1 152 |
| 17 | 4 352 |
| 16 | 16 384 |
| 15 | 61 440 |
| 14 | 229 376 |
| 13 | 851 968 |

把各个规模代进去算填充率：

| 4 096 | 512 | 18 | 1 821 | 2 048 | 1.12× | — |

**看 `65 536 hex` 那行：`coeffs = 32769`，只比 `2^15 = 32768` 多 1，
FFT 长度就从 32768 跳到 65536 —— 整整一倍的运算量花在补零上。**

## 3. 两条可行路线（你可以选一条，或都做）

### 路线 A1：精确精度模型 —— 把 `gk` 表推到真正的边界

`gk` 表是**经验值**，多半是保守的。如果 `k=17` 实际能安全覆盖到 `u = 8192`（而不是表里的 4352），
那么上表的 `65 536 hex` 一行就直接省掉 50%，**改一个常量表即可，零风险重构**。

需要你做的事：

1. **推导严格的误差上界。** 浮点 FFT 卷积的误差上界（Percival / Brent-Zimmermann 体系）大致形如：

   ```
   |err| ≤ ‖a‖·‖b‖ · ((1+ε)^(3n) · (1+ε√5)^(3n) · (1+ε)^... − 1)
   ```

   实用近似（Colin Percival, "Rapid multiplication modulo the sum and difference of highly composite numbers", 2003）：

   ```
   E ≤ |x|·|y| · ((1+ε)^(3n) (1+ε√5)^(3n-3) (1+ε)^(3n-1) − 1)
   n = log2(FFT_len),  ε = 2^-53
   ```

   其中 `|x|·|y|` 对本问题 = `coeffs_half · (2^k − 1)^2`（复数打包后参与卷积的项数 × 最大系数积）。

   **请给出：对每个 `k ∈ [10, 19]`，在 `max_err < 0.25` 约束下，`u` 的严格上界。**
   （0.25 而不是 0.5，是为了留 2× 安全余量）

2. **注意本实现的两个特殊点，会影响误差模型：**
   - **实数打包**：两个相邻实系数打进一个复数（`re`, `im`），
     用 `pointwise` 时做的是 "两路实卷积"的合成，误差比裸复卷积略大
   - **`pointwiseSq`**（平方专用路径）误差特性与 `pointwise` 不同

3. **实测验证。** 构造最坏输入（两个操作数全 `f`，即所有 limb = `0xFFFFFFFFFFFFFFFF`），
   在 `merge_b2` 里插桩记录 `max |g[j] − round(g[j])|`，
   扫描每个 `(k, u)` 组合找真实断点，与你的理论上界对照。

4. **交付**：新的 `gk` 表 + 理论推导 + 实测断点对照表。

> **这条路的好处：改动极小（一个 `static const size_t gk[11]`），风险可控，收益可能立刻兑现 50%。**
> **请优先做这条。**

---

### 路线 A2：非 2 幂 FFT 长度（混合基 radix-3 / radix-5）

即使 `gk` 表推到极限，2 的幂的粒度仍然是 2×，平均浪费 ~1.4×。
支持 `3·2^m` 和 `5·2^m` 后，可选长度序列变成：

```
... 2048, 2560, 3072, 4096, 5120, 6144, 8192, 10240, 12288, 16384 ...
     2^11  5·2^9 3·2^10 2^12  5·2^10 3·2^11 2^13  5·2^11  3·2^12  2^14
```

**粒度从 2.00× 降到 1.25×，平均浪费从 ~1.4× 降到 ~1.12×。**

需要实现：
- **radix-3 蝶形**（DIF + DIT），复数版，`__m128d`
  ```
  w3 = exp(-2πi/3) = (-1/2, -√3/2)
  X0 = x0 + x1 + x2
  X1 = x0 + w3·x1 + w3²·x2
  X2 = x0 + w3²·x1 + w3·x2
  ```
  用 `t = x1 + x2`, `d = x1 - x2`：
  ```
  X0 = x0 + t
  m  = x0 - t/2
  s  = (√3/2)·i·d
  X1 = m - s
  X2 = m + s
  ```
  → 每个 radix-3 蝶形约 12 flop（vs radix-2 的 8 flop 处理 2 点），
  单点成本 4.0 vs 4.0 —— **持平**，但省下的是"长度浪费"

- **radix-5 蝶形**（可选，收益小于 radix-3，实现复杂度高不少）

- **自排序（self-sorting）版本**：现役 FFT 是自排序 radix-4，**没有 bit-reversal 置换步骤**。
  混合基必须同样做到自排序，否则要引入 digit-reversal 置换，那是一次额外的全数组随机访问，
  在访存受限的场景下会把收益全吃掉。
  推荐参考 **Temperton 的 self-sorting mixed-radix FFT**（*J. Comput. Phys.* 52 (1983) 1–23）
  的 in-place self-sorting 变体。

- **twiddle 表适配**：现役是两级表 `w[i] = twbase[halfSize|(i>>halfLog)] · twbase[i&halfMask]`，
  长度非 2 幂后索引拆分要重新设计（见 §5 陷阱）。

**交付**：完整 `.cpp` + 长度选择函数 + 性能对比。

## 5. 陷阱（务必看完）

### 5.1 `lm` 恰为 2 的幂时会白白翻倍
`lm = 2u << (31 - __builtin_clz(coeffs))`。
当 `coeffs` 恰好是 2 的幂（如 32768）时，这个式子给出 `65536`，多用一倍。
正确的 `next_pow2` 应该是 `coeffs <= (1u<<m) ? (1u<<m) : ...`。
**但注意**：现役代码依赖 `lm >= coeffs` 且卷积不能回卷（circular wrap），
改之前请确认 `coeffs` 的定义已经含了"结果长度"而不是"操作数长度"。
（读 `mul_fft` 与 `merge_b2` 确认）

### 5.2 `zero-hi` 优化会跟长度选择耦合
```cpp
const size_t half = lm >> 1;
const size_t ta = split_b2(a, FB, na, k, deep ? half : lm);
const bool hiA = deep && ta <= half;   // 单操作数系数数 <= lm/2 时走 ZeroHi 快路径
```
如果你把 `lm` 缩小了一半，原本满足 `ta <= half` 的输入可能不再满足，
**ZeroHi 快路径失效，可能把省下的收益吃回去一部分**。
请在做 A/B 时统计 ZeroHi 命中率的变化。

### 5.3 两级 twiddle 表的高位分量不能无条件外提
详见 `TASK_B_radix16_butterfly.md` §8.1。这是前人踩过的真实 bug（小 FFT 才炸，大 FFT 全对）。
如果你要改 twiddle 索引方式，务必读那一节。

### 5.4 小规模才暴露 bug
分档逻辑的 bug 几乎总是在 **小规模**（1~600 limb）暴露，大规模反而全过。
压测必须覆盖小规模，且要**大量**。

### 5.5 `-O2` 不是 `-O3`
再说一遍。

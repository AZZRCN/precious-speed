## 1. 问题定义

标准输入：
```
T
A_1 B_1
A_2 B_2
...
A_T B_T
```
- `T ≤ 200000`
- 每个 `A_i`、`B_i` 是 16 进制串，可带前导 `-`，无前导零（`0` 除外）
- 单个操作数最长 **1 600 000 hex 位**（= 100 000 个 64-bit limb）
- 所有输入总长 ≤ 约 8 MiB
- 输出 `A_i * B_i` 的 16 进制表示，每行一个，小写字母

## 2. 评测机口径（**极其重要，A/B 测试必须严格遵守**）

```
g++ -O2 -march=x86-64-v3 -std=c++23
```

- **`-O2`，不是 `-O3`**
- **`-march=x86-64-v3`，不是 `-march=native`**
- **提交目标机：AMD Zen3**（EPYC / Ryzen 5000 系）。`x86-64-v3` = SSE*, AVX, AVX2, FMA, BMI1/2, LZCNT, MOVBE, POPCNT
- **测量机（Linux VM）：Intel Tiger Lake（i7-11370H，AVX2+FMA）**。注意 Tiger Lake 硬件支持 AVX-512，但我们用 `-march=x86-64-v3` 已把它排除，使二进制对 Zen3 与目标机一致
- **禁止 `#pragma GCC optimize(...)`**（提交环境会拒绝或行为不可预期）
- **禁止 AVX-512**（Zen3 没有，且 `-march=native` 在 Tiger Lake 上会误生成 EVEX 指令）

> ⚠️ 我们在这上面栽过一次大跟头：一个版本用 `-O2`、另一个误用 `-O3 -march=native`
> 做 A/B，测出 −3.46% 的"提升"；统一口径后只剩 −1.12%。
> **近 2.4 个百分点完全是编译选项冒充的。**
> 任何 A/B 数据，两侧必须是**逐字符相同的编译命令**。

Zen3 关键微架构参数（供你做指令级预算）：
| 项 | 值 |
|---|---|
| L1D | 32 KiB, 8-way, 64B line, 4–5 cyc |
| L2 | 512 KiB, 8-way, ~13 cyc |
| L3 | 32 MiB/CCX（共享）, ~46 cyc |
| FP 端口 | FMA ×2（FP0/FP1），FADD ×2（FP2/FP3） |
| `vfmadd*pd` | lat 4, thr 0.5 |
| `vmulpd`/`vaddpd` | lat 3, thr 0.5 |
| `vpermilpd`/`vshufpd` | lat 1, thr 0.5（FP1/FP2） |
| L1D 读 | 2×/cyc（32B 各） |
| L1D 写 | 1×/cyc（32B） |
| ROB | 256 |

## 3. 现役算法（v10c）

```
输入解析（AVX2 hex → u64 limb）
    ↓
la ≤ 32 且 lb ≤ 32  →  __uint128_t 4 次 mulx 直算
    ↓
mb ≤ 48 limb        →  Comba schoolbook（u128 累加）
    ↓
其余                →  浮点 FFT 卷积
```

FFT 部分：
- **实数打包成复数**（两个相邻实系数 → 一个 `__m128d`），只做一半长度的复 FFT
- **自排序 radix-4 DIF/DIT**（无 bit-reversal 置换）
- 蝶形用 `__m128d` + FMA（`_mm_fmaddsub_pd`）
- **两级 twiddle 表**：`twbase[4096]`，`w[i] = twbase[halfSize | (i>>halfLog)] * twbase[i & halfMask]`
  → 表从 512 KiB 降到 16 KiB，D1 miss −11%，LLd −25.9%
- **zero-hi 优化**：单操作数系数数 ≤ lm/2 时，实数缓冲上半恒为零，顶层 radix-4 只做下半
- 位分割 `split_b2`：把 limb 流按 k 位一组切成 double 系数（AVX2 `vpgatherdd`）
- `pick_k(u)` 按结果 limb 数 u 选 k（精度分档表，见任务 A）

## 4. 当前瓶颈画像（cachegrind + perf 实测，已确认）

- **访存受限，不是端口受限**。FP 端口占用各仅 ~39%
- 29 M 停顿周期中 **19.8 M 是 `cycle_activity.stalls_mem_any`**
- 经验换算：**每降 1% D1 miss ≈ 换 0.143% 墙钟**
- `Ir`（指令数）**不是**判优指标 —— v10c 比 v9 的 Ir 高 3.93%，墙钟反而快 1.12%
- 系统层已封顶：THP 已生效（AnonHugePages 88%）、syscall 全程仅 49 次

**结论：任何优化，只有降低"实际参与运算的数据量"或"访存流量"才可能赢。
纯粹减少指令数的优化，在这里基本无效。**

## 5. 验证要求（**不可跳过，不可互相替代**）

任何改动，必须**先过正确性，再谈性能**：

### 5.1 随机压测
用附带的 `stress_mul.py`（或你自己写等价物），至少：
- 400 轮 × 4 个不同 seed
- 每轮随机生成若干组 `(a, b)`，长度覆盖 **1 ~ 100 000 limb**，
  **必须包含大量小规模**（1~600 limb），因为算法分档的 bug 只在小规模暴露
- 与 Python `int` 结果逐字节比对

> ⚠️ 真实教训：有个版本在大输入（≥ 2^20 点 FFT）全过，
> 但在 `63 × 513 limb`、`97 × 64 limb` 上错。**大输入全过 ≠ 正确。**

### 5.2 官方测试点
22 个 Library Checker 官方点，输出与已知正确版本**逐字节一致**。

### 5.3 精度余量
如果你动了 `pick_k` / 位宽 / FFT 长度，还必须做**精度余量测试**：
构造最坏输入（全 `f`），检查 `|round(x) - x|` 的最大值。
安全线：**max_err < 0.25**（留 2× 余量）。

### 5.4 性能测量
- 必须在 **Linux + 真实 x86 CPU** 上测，Windows 数据一律不可信
- 必须 **ABBA 交替 + ≥ 21 组配对 + 符号检验**，只报中位数比值和 p 值
- 单次或少次测量的"快了 x%"一律视为噪声
